# 产品方案：Solo Delivery 模板验证与 Java DDD 参考工程

## 1. 背景

`solo-delivery` 已经具备完整阶段和初版模板，但模板内容、填写边界和工程约束尚未通过真实项目验证。本方案把 `ddd` 作为一次完整交付：一方面让使用者逐阶段查看和校准文档模板，另一方面生成可复用的 Java DDD 参考工程，最终为公共 Skill 提供经验证的改进依据。

## 2. 产品目标与非目标

### 2.1 产品目标

- 让每个阶段“生成什么、为什么生成、什么是完成”清晰可见。
- 将用户材料、AI 生成文档、机器状态和 Java 源码分区管理。
- 把后续 DDD 规范转换为可执行的工程模板、示例和检查规则。
- 用完整的开发、CR、测试和复盘证明模板可用，而不是只产出说明文档。

### 2.2 非目标

- 不替代具体业务项目的领域建模。
- 不在 DDD 材料到达前确定最终分层细节。
- 不制作没有实际用户界面的 UI 方案。
- 不自动把项目经验写回公共 Skill。

## 3. 用户角色与核心场景

| 角色 | 核心任务 | 期望结果 |
|---|---|---|
| 项目发起人/审批者 | 提供背景与材料，确认范围、产品和技术决策 | 随时看懂当前产物和下一项决定 |
| AI 业务/产品角色 | 从输入材料形成可评审需求和产品方案 | 不发明事实，暴露假设和缺口 |
| AI 开发角色 | 按已批准规则生成 Java DDD 参考工程 | 代码可编译、结构可解释、调用可追踪 |
| AI CR 角色 | 独立检查实现正确性和工程风险 | 产生可定位、可修复的 CR 结论 |
| AI 测试角色 | 从需求视角设计用例并验证行为 | 产生独立于开发自测的验收证据 |
| 模板维护者 | 评估本项目暴露的模板问题 | 只吸收有依据且经确认的通用改进 |

## 4. 方案摘要与原则

### 4.1 方案摘要

以 `.ai-delivery` 维护流程状态，以 `AI/input` 接收素材，以 `AI/output` 展示生成文档，以 8 个 Maven 子模块承载 Java 代码。参考工程不绑定真实业务，统一以 `Ddd*` 作为可替换占位符；真实项目生成代码时，应按业务语义替换为 `Order*`、`Customer*` 等名称，而不是沿用 `Ddd*`。

### 4.2 产品原则

1. **可见**：模板章节、状态、假设和缺口直接体现在 Markdown 中。
2. **单一事实源**：同一生成文档只保留一个可编辑版本。
3. **按需完整**：模板提供质量下限，但允许明确标记不适用。
4. **先约束后编码**：DDD 规则确认后再初始化最终 Java 结构。
5. **证据驱动迭代**：公共模板变更必须关联本项目的具体问题或返工。
6. **角色分离**：开发自测、代码审查和独立测试不互相替代。

## 5. 实现手段（产品层）

| 能力 | 产品实现手段 | 关联需求 |
|---|---|---|
| 输入管理 | 用户将规范、示例、图片或文档放入 `AI/input`，并在 `00 输入材料清单.md` 中登记来源和权威级别。 | REQ-F-005、REQ-F-010、REQ-F-012 |
| 阶段文档 | 每个阶段在 `AI/output` 生成独立 Markdown，使用固定两位序号、中文名称、元数据、固定章节、稳定 ID 和变更记录。 | REQ-F-001～REQ-F-004、REQ-F-012、REQ-NF-001 |
| 流程连续性 | `.ai-delivery` 保存 JSON/YAML 机器状态和配置，`AI/output` 保存带序号中文名的批准、假设、问题和交接文档。 | REQ-F-009～REQ-F-012 |
| DDD 规则化 | 对输入规范逐条提取规则，标记强制/推荐/禁止/待澄清，并映射到设计、代码和检查。 | REQ-F-005、REQ-NF-003 |
| 参考工程 | 用 `Ddd*` 中性占位类型分别展现写、域内读、规则+计算、纯计算及外部读调用链。 | REQ-F-006、REQ-F-007 |
| 模板评估 | 每阶段记录缺失、冗余、歧义和返工，在复盘形成公共模板修订候选。 | REQ-F-008、REQ-NF-005 |

## 6. 信息架构与目录

```text
ddd/
├── AI/
│   ├── input/                    # 用户提供给 AI 的材料
│   │   └── 00 输入材料清单.md
│   └── output/                   # AI 生成的带序号中文 Markdown 文档
│       ├── 01 需求文档.md
│       ├── 02 产品方案.md
│       ├── 04 技术方案.md
│       └── 其他阶段产物
├── .ai-delivery/                 # 机器状态和配置
│   ├── state.json
│   └── project-profile.yaml
├── ddd-client/                   # 对外请求、响应和统一结果协议
├── ddd-model/                    # 跨边界内部模型
├── ddd-domain/                   # 聚合、实体、值对象、领域服务和仓储端口
├── ddd-application/              # 用例编排和外部调用端口
├── ddd-infrastructure/           # MyBatis-Plus 持久化实现
├── ddd-adaptor/                  # input/output adaptor 与模型转换
├── ddd-start/                    # Spring Boot 启动、装配和集成测试
└── pom.xml                       # Maven 聚合父工程
```

Skill 已原生使用 `AI/input` 和 `AI/output`，`.ai-delivery` 仅保存机器状态和配置，不再创建英文名产物目录或文档副本。

## 7. 核心流程

### FLOW-001 新材料进入

1. 用户将材料放入或引用到 `AI/input`。
2. Agent 登记来源、权威级别、适用需求和限制。
3. Agent 提取事实、规则、假设、冲突和开放问题。
4. 无法读取或存在冲突时停止受影响的路径并请求补充。

### FLOW-002 阶段文档生成与确认

1. Agent 读取当前状态、已批准上游文档和本阶段模板。
2. 在 `AI/output` 生成或修订 Markdown。
3. 执行结构与追踪校验。
4. 展示关键结论、假设和待决定项。
5. 用户确认后记录审批并进入下一阶段；修改则标记下游为失效待复核。

### FLOW-003 DDD 规范转化

1. 用户提供 DDD 规范及可选参考工程。
2. Agent 生成规则目录，区分强制、推荐、禁止和冲突。
3. 用户确认规则解释及适用范围。
4. Agent 将规则映射到技术方案、任务、代码示例、静态检查、CR 和测试。

### FLOW-004 参考工程交付

1. 按技术方案初始化 Java Maven 多模块工程和 DDD 分层。
2. 以 `Ddd*` 中性占位类型实现四种 DDD 模式和外部读链路。
3. 完成开发自测并生成开发报告。
4. 独立执行 CR，修复后复查。
5. 根据需求设计独立用例并测试，输出缺陷和验收结论。

### FLOW-005 模板反馈闭环

1. 每阶段记录模板问题和造成的实际影响。
2. 复盘时区分项目偏好、Java/DDD 专用规范和通用规范。
3. 提交“修改前、修改后、收益、兼容影响”的候选方案。
4. 只有用户明确确认后，才更新并重新发布公共 Skill。

## 8. 功能详细设计

| 功能 | 前置条件 | 主流程 | 异常与恢复 | 结果 |
|---|---|---|---|---|
| 文档模板生成 | 阶段及输入已识别 | 套用模板、填充内容、标注不适用和待确定项 | 缺少关键决策则停在关口 | 可评审 Markdown |
| 输入素材接收 | 宿主可读取材料 | 登记、解析、关联需求 | 不支持格式则请求转换或提供文本 | 可追踪来源 |
| DDD 规则抽取 | DDD 材料已提供 | 逐条分类、解释、编号和映射 | 冲突或歧义交由用户决策 | 可执行约束目录 |
| Java 参考工程 | 技术方案已批准 | 生成结构、示例调用、测试与说明 | 构建失败返回开发修复 | 可运行工程 |
| 模板评估 | 阶段产物已使用 | 记录问题、证据和修订候选 | 缺少通用性证据则保留项目内 | 可审批改进项 |

## 9. 文档生命周期与状态

| 状态 | 含义 | 允许进入条件 | 后续动作 |
|---|---|---|---|
| draft | 正在形成内容 | 已有初始输入 | 补全并自检 |
| review | 内容可供语义评审 | 结构、追踪和显著缺口已检查 | 用户确认或提出修改 |
| approved | 用户认可内容含义 | 通过阶段关口 | 进入下游阶段 |
| stale | 上游变化可能影响结论 | 发现依赖变化 | 完成影响分析并重审 |
| skipped | 阶段不适用 | 用户确认且记录原因 | 直接进入下一有效阶段 |
| blocked | 关键输入或决策缺失 | 无法安全继续 | 等待材料或决定 |

## 10. 业务规则与校验

| ID | 规则 | 校验方式 |
|---|---|---|
| RULE-001 | 人类可读交付文档使用 Markdown。 | 扩展名与结构校验 |
| RULE-002 | JSON/YAML 仅用于机器状态和配置。 | 目录及文件类型检查 |
| RULE-003 | 同一生成文档不得在 `.ai-delivery` 与 `AI/output` 形成两个独立副本。 | 目录结构检查 |
| RULE-004 | 未知内容必须标为待确定、假设或开放问题。 | 文档评审 |
| RULE-005 | DDD 规范未确认前不得固化最终代码结构。 | 技术关口检查 |
| RULE-006 | UI 无实际内容时跳过，不生成占位方案。 | 状态与决策记录 |
| RULE-007 | 公共 Skill 不由项目自动改写。 | 变更范围检查 |
| RULE-008 | 开发、CR、测试分别出具证据。 | 阶段产物校验 |
| RULE-009 | 生成文档和 Skill 内非协议 Markdown 资源使用中文文件名，固定协议入口保留标准名称。 | 文件名清单校验 |
| RULE-010 | 生成文档使用两位阶段序号前缀，确保 Finder、IDE 和不同宿主均可按交付顺序排列。 | 初始化、迁移和目录清单校验 |

## 11. 推演可行性

| 维度 | 结论 | 依据与限制 |
|---|---|---|
| 使用可行性 | 可行 | 输入、输出和状态职责清晰，用户可以直接浏览 Markdown。 |
| 流程可行性 | 可行 | 当前 Skill 已有阶段状态、审批、追踪、校验和交接能力。 |
| 技术可行性 | 已验证 | DDD 规范、JDK 17、Spring Boot 3.x、Maven、MyBatis-Plus 和模块边界已经落地，并通过本地构建与测试。 |
| 跨宿主可行性 | 可行 | 直接使用普通目录，不依赖符号链接；仍需验证不同宿主对中文路径的处理。 |
| 模板产品化 | 有条件可行 | 必须先完成本项目、记录真实问题并验证哪些规则具有通用性。 |
| 成本风险 | 可控 | 通过按需章节和跳过 UI 降低文档负担；Full 流程仍需要多次语义确认。 |

## 12. 角色、权限与数据边界

- 用户拥有业务规则、范围、技术约束和发布决定的最终审批权。
- Agent 可在已批准阶段内生成文档、代码和本地验证证据。
- 未明确授权时，Agent 不执行部署、合并、发布、生产写入或外部消息。
- 输入材料中的敏感信息不得复制到日志、示例代码或公共 Skill。

## 14. 兼容性与降级

- 有文件和 Shell 能力的编码宿主执行完整流程。
- 只有文档能力的宿主可以生成 Markdown，但必须把编译、CR 执行和测试标为未运行。
- 宿主必须按 UTF-8 处理中文路径；若宿主不支持，应明确报告兼容性限制，不回退为两套文件名。
- 不依赖聊天历史恢复批准结论，始终以项目状态和交接记录为准。

## 15. 本期范围与后续范围

### 15.1 本期

- 确认需求与产品模板。
- 建立 `AI/input`、`AI/output` 与机器状态分离结构。
- 接收并解析 DDD 规范。
- 设计并实现 Java DDD 参考工程。
- 完成开发自测、CR、独立测试、发布检查和复盘。

### 15.2 后续

- 将确认后的文档模板和代码参考抽取到 `solo-delivery`。
- 验证中文路径在不同宿主、操作系统和压缩包中的兼容性。
- 根据真实项目反馈扩展其他语言或架构模板。

## 17. 风险、假设与开放问题

- `Ddd*` 仅表达层级和调用模式，不能替代真实项目的领域分析；生成真实代码时必须使用业务语义命名并重新建模。
- 中文文件名需要在 Windows、压缩包和其他宿主中验证编码与解压行为。
- 产品模板目前较完整，后续应通过真实填写识别哪些章节必须、按需或可合并。
