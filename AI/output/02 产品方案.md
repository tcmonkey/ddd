# 产品方案：solo 一人交付与 DDD 模板验证

## 1. 背景、目标与非目标

目标是让一个开发者依照技能完成项目或项目中的需求：输入背景与素材，确认 AI 理解，逐阶段形成方案、实现、质量证据、发布运行和效果评价。ddd 是验证这套能力的参考工程，不是某个真实积分、订单业务。

产品成功体现为“决策明确、代码有规则、质量有证据、跨会话可继续”，不体现为预先生成大量空文档。UI、专项计划和性能专项按需求风险裁剪。本轮不新增代码与真实生产能力。

## 2. 用户、实现手段与信息结构

| 使用者/角色 | 任务 | 可见产物 |
|---|---|---|
| 用户/审批者 | 输入背景、规范与限制，查看理解并作关键决定 | 需求、方案、工作台检查点 |
| AI 开发者 | 按计划及规范生成真实业务代码，执行开发自测 | 代码与开发交付记录 |
| AI 审查者 | 从实际差异识别工程缺陷 | 同文档中的独立 CR 范围、发现与复查 |
| AI 测试者 | 根据需求设计并执行验收，不把单测当验收 | 测试验收报告 |
| 运行/评估角色 | 在授权下发布、观测、放量、回退和评价价值 | 发布运行记录、效果评估与复盘 |

```text
ddd/
├── AI/
│   ├── input/00 输入材料清单.md    # 素材和来源
│   └── output/                    # 按需主文档，00～08；19 编码规范
├── .ai-delivery/                 # 状态、配置、只读历史归档
├── ddd-common/                   # Result、ErrorCode、BaseException
├── ddd-client/                   # 对外 Request/Response，按需 RPC 接口
├── ddd-model/                    # 项目内部共享 DO，不含业务行为
├── ddd-domain/                   # 聚合、实体、值对象、领域服务和仓储端口
├── ddd-application/              # Command、Result、assembler、编排与外部端口
├── ddd-infrastructure/           # PO、Mapper、MyBatis-Plus 仓储实现
├── ddd-adaptor/                  # input 协议收口、output 外部防腐
├── ddd-start/                    # 启动、显式装配、数据库和日志配置
├── checkstyle.xml               # 构建语法约束
└── pom.xml                      # 聚合、版本管理和继承门禁
```

## 3. 主文档与完整用户流程

| 顺序 | 文件/位置 | 生成时机与用户行为 |
|---|---|---|
| 00 | 交付工作台 | 初始化；随阶段更新索引、决策、追踪、问题与交接 |
| 01 | 需求文档 | 读取材料、展示理解后形成范围与验收，请用户确认 |
| 02 | 产品方案 | 范围确认后生成；小需求并入 01，不复制一份内容 |
| 03 | 界面设计方案 | 只有实际界面变化才生成 |
| 04 | 技术方案 | 产品明确后；架构、核心伪代码和计划可直接指导编码 |
| 05 | 开发交付记录 | 编码开始后；自测和 CR 分节、各自判定 |
| 06 | 测试验收报告 | 进入独立测试；用例、结果、缺陷、复测及按需专项 |
| 07 | 发布运行记录 | 进入发布准备；顺序记录真实执行、观测和放量 |
| 08 | 效果评估与复盘 | 有可评估产物/发布窗口后；记录效果数据与改进候选 |

主路径：需求 → 产品 → 可选 UI → 技术与计划 → 编码 → 开发自测 → CR → 独立测试 → 发布准备 → 初始发布 → 观测 → 分批放量 → 完整发布确认 → 效果评估。

步骤可以共用文件，不能共用一份“通过”结论。初始化仅工作台、输入清单和状态；未开始的测试、发布、评估文件不生成。复杂项目确需独立任务或专项性能报告时才拆分，主文档保留摘要和唯一位置链接。

## 4. 产品规则、状态与异常恢复

| 规则 | 正常行为 | 异常/恢复 |
|---|---|---|
| 来源可追踪 | 记录文字、图片、文件、链接来源与权威性 | 无法访问材料则说明限制，请补充，不假装已读 |
| 先理解后实施 | 先确认范围和方案，在授权阶段内执行 | 关键业务决策缺失时停在关口 |
| 状态独立 | state.json 维护每个阶段，工作台同步展示 | 上游改变则受影响阶段 stale，重新验证 |
| 自测/CR/测试隔离 | 运行证据、工程评审、需求验收各有目标 | 测试缺陷返回编码、自测、受影响 CR 与复测 |
| 顺序跨宿主交接 | 读取共同状态和 revision 后继续 | 版本冲突重新协调，不覆盖新状态 |
| 发布授权明确 | 准备方案后确认环境、版本、范围和窗口 | 未授权不能部署，下一批超出范围须确认 |
| 指标驱动放量 | 基线、阈值、窗口和样本满足才继续 | 异常、缺数据或样本不足则暂停或回退 |
| 完整确认与价值分离 | 全量覆盖并稳定后确认发布；再统计效果 | 部署稳定不等于用户价值达标 |
| 公共模板受控 | 项目内先记录候选，有授权才同步技能 | 项目偏好不自动改写公共规范或快照 |

not_started、in_progress、review、approved、skipped、stale、blocked、complete 保持机器状态标准值。文档 frontmatter 是整份记录的总体状态，不能据此推断其中每个阶段均已完成。

## 5. 参考工程与推演可行性

ddd 用 Ddd 中性占位展示四种模式及外部读的五条链路。真实需求按业务语义生成 OrderApplication 等名称，仅选择所需链路、层和模型，不能复制演示接口凑齐结构。

| 维度 | 当前结论 | 限制 |
|---|---|---|
| 文档组织 | 9 份主文档、输入素材、机器状态分区可行 | 本次重新生成版本仍需实际阅读反馈 |
| 代码复用 | 规则、代码快照及 Checkstyle 已配套 | 自动语法检查不能验证完整 DDD 或业务正确性 |
| 本地运行 | 历史 Maven 自测 3/3；H2/MyBatis-Plus/MockMvc 链路可跑 | H2、空规则表及外部模拟不是生产实现 |
| 跨宿主 | 共享内核、普通项目文件和 revision 交接 | 本次不声称 Claude Code/Qwen Code 已做真实端到端验收 |
| 发布闭环 | 技能已定义准备、观测、放量、回滚和效果评价 | ddd 尚无生产发布授权、环境和指标 |
| 一人独立验收 | 可以切换审查/测试视角并形成独立证据 | 同一人/模型仍存在盲点，关键系统应增加外部复核 |

## 6. 范围、验收与度量

当前文档应体现需求 F001～F014，具体追踪在工作台。工程入口和代码规则见技术方案及 19 规范，不在产品文档复制另一份编码条例。

| 指标 | 目标 | 当前判定 |
|---|---|---|
| 文档负担 | 初始化无未来空报告；关键证据合并可读 | 结构回归测试验证，不以主文档数量证明质量 |
| 需求追踪 | 所有已批需求能定位设计与后续验收 | 当前已梳理；CR/独立测试覆盖待执行 |
| 工程可构建 | 约定门禁及自测通过 | 沿用历史 3/3，新的业务验收未执行 |
| 模板约束清晰 | 当前规范与快照一致，不使用已废弃规则 | 19 规范为唯一规则副本 |
| 发布与效果 | 有真实运行数据和评价口径 | 尚未开始，不能填造成功率或收益 |

风险：文档仍需按真实需求裁剪；独立 CR、生产数据库、鉴权、并发、真实第三方和性能尚未充分验证。发布范围应先确定为“模板发行验收”还是“服务部署”，不得自行升级为生产项目。

## 7. 变更与审批边界

原产品 0.1～0.6 的形成、八模块和 common 调整记录保留在迁移归档。1.0 按用户 SRC-039 批准的流程/主文档布局重整，统一 solo 名称并修正当前信息结构；不追加代码、独立验收或生产效果完成结论。
