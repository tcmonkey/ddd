# 需求文档：solo 元需求与 Java DDD 参考工程

> 本版按 solo 0.8 重新组织已确认范围。历史审批绑定原版文档，不新增“已完成 CR、测试或生产发布”的结论；原文和审批可从交付工作台追溯。

## 1. 诉求调研

希望一个人借助 AI 顺序完成传统业务、产品、设计、开发、审查、测试和发布工作。技能不仅应规定流程，还要提供看得懂、可填写、能约束真实代码的模板。

本项目是“元需求”：用 ddd 工程实际校准 solo，将已经讨论并确认的 Java DDD 约束整理为唯一规范，配合干净代码快照和编译门禁，供后续真实需求按业务语义生成代码。

用户既是需求发起人和开发人员，也是阶段审批者；AI 在不同阶段切换职责。独立测试指独立于实现的需求视角与验收证据，不保证存在另一位真人或另一个模型。

## 2. 背景与现状

- ddd 已形成八模块 Maven 参考工程，覆盖写、域内读、规则计算、纯计算和外部读。
- DDD 材料已收到，后续命名、模型、转换、仓储、异常、注释及版本约定已沉淀为 [19 Java DDD开发规范](<19 Java DDD开发规范.md>)。
- Java 代码已完成多轮调整及开发自测。当前状态停在 CR 尚未开始；独立测试、发布及效果评估尚无完成证据。
- 旧文档逐轮追加，存在已过时描述及碎片记录。本次只调整技能流程、文档结构与交付元数据，不修改 Java 代码、POM、配置或检查规则。

## 3. 期望、预期价值与成功指标

| 价值 | 期望 | 验证方式 |
|---|---|---|
| 一人交付 | 每一步输入、输出、完成条件及下一决定清晰 | 用一个新项目裸调用 solo，能从需求理解逐步接续 |
| 文档可读性 | 9 份主文档按需生成，中文编号，无未来空报告 | 初始化清单、阶段文件生成及结构测试 |
| 工程复用 | Java DDD 规则、示例和自动检查一致 | 规范 C/P/R 对照、示例链路走查、Maven 构建 |
| 质量闭环 | 编码、自测、CR、独立测试不互相替代 | 各阶段独立状态、审查发现与验收证据 |
| 发布价值 | 真实发布具备观测、放量、回滚及效果评价 | 有基线、阈值、窗口、数据和明确授权；本工程暂未执行 |

目标不是文档越多越好。以“能指导实现并保留关键决策”为下限，根据需求大小合并或省略不适用内容。生产价值尚未统计，不能宣告已经达标。

## 4. 范围与功能需求

| ID | 正式需求 | 可观察验收标准 |
|---|---|---|
| REQ-F-001 | 各阶段有明确模板、填写边界和完成条件 | 当前阶段使用相应模板；未知、假设和不适用明确 |
| REQ-F-002 | 需求覆盖诉求调研、背景、期望价值、范围及验收 | 需求有稳定 ID，边界和成功条件可检查 |
| REQ-F-003 | 产品覆盖背景、实现手段、用户流程、规则及可行性 | 产品方案可追踪到需求，异常与范围取舍明确 |
| REQ-F-004 | 技术呈现架构、模型、伪代码、接口及可靠性闭环 | 读完可确定调用顺序、关键分支、风险与验证方法 |
| REQ-F-005 | 接收 DDD 材料并归纳生效约束 | 规范区分必须、禁止、按需及 C/P/R，不按旧决策生成代码 |
| REQ-F-006 | 形成实际可复用 Java DDD 工程 | 八模块可构建，典型完整链路可读取和验证 |
| REQ-F-007 | 展示命名、转换、模型行为、仓储、错误及注释 | 示例与规范对应，结构性语法有自动门禁，架构仍有审查 |
| REQ-F-008 | 记录模板问题、返工及修订依据 | 改进有证据、适用范围和修改前后描述；写回公共技能需授权 |
| REQ-F-009 | 支持不同编码宿主顺序接续 | 读取状态、工作台及 revision 可定位下一步，不依赖聊天记忆 |
| REQ-F-010 | 分离素材、文档、状态和代码 | AI/input、AI/output、.ai-delivery 与各模块源码职责分明 |
| REQ-F-011 | 非协议文档采用中文名称 | 主模板及阶段规范中文；SKILL.md 等协议入口不改名 |
| REQ-F-012 | 中文文档使用两位序号排序 | 00 工作台、01～08 主文档；输入清单独立为 00，编码规范副本为 19 |
| REQ-F-013 | 技术文档紧凑、核心伪代码必填，按规模裁剪 | 五个主体章节，整体方案包含代码逻辑及默认嵌入开发计划 |
| REQ-F-014 | 收敛文档且补齐完整发布与价值闭环 | 初始化仅工作台/输入清单；自测/CR、发布子阶段状态独立；不编造未来证据 |

REQ-F-001～013 沿用原需求编号与语义；REQ-F-012 的旧 01～18 一阶段一文件布局由本次 SRC-039 明确替换。SRC-039 是本轮用户批准，补充来源登记见工作台，原始输入清单不修改。

非目标：不建设具体生产业务、真实 UI、真实第三方连接或生产 MySQL；不因调整流程就改 Java；不自动合并、远程发布、生产操作或修改公共模板；不为小需求虚构用例与放量数据。

## 5. 非功能需求

| ID | 要求 | 验证 |
|---|---|---|
| REQ-NF-001 | 人类交付文档 Markdown、中文编号，机器 JSON/YAML 例外 | 文件名和元数据结构校验 |
| REQ-NF-002 | 来源—需求—方案—任务—代码—自测—CR—测试—发布/效果可追踪 | 工作台覆盖矩阵与缺口检查 |
| REQ-NF-003 | 约束尽可能可重复验证，说明自动检查边界 | C/P/R 规则及编译前违规反向用例 |
| REQ-NF-004 | 示例中性、可替换为业务语义 | Ddd 占位命名、所需链路选取和生产适配清单 |
| REQ-NF-005 | 修改有版本、原因、影响和历史恢复能力 | 工作台与迁移原文/校验和 |
| REQ-NF-006 | 工程能通过约定构建与自测，不把未运行算通过 | 开发交付记录中的真实命令与结果 |

## 6. 规则、约束与依赖

1. 当前编码规则以 19 规范及获批项目约定为准，历史被替换的字段注入等决策不再生效。
2. 小需求产品内容可并入需求；无界面则跳过 UI；开发计划默认内嵌技术方案。专项拆分须有理由和唯一来源。
3. 每个阶段分别判定。自测通过不自动 CR 通过，模板报告齐全不自动测试验收，部署成功不自动放量及价值达标。
4. 技术授权不扩大为 Git 合并或生产部署授权；初始发布和每批放量在明确授权范围内执行。
5. H2、JSON 快照、空规则表和外部模拟只是演示，真实项目必须重新评估模型、数据库、鉴权、观测与回滚。
6. 当前使用 JDK 17、Spring Boot 3.3.12、Maven/MyBatis-Plus；不把本工程版本机械强加给已有项目。
7. 代码、检查配置和干净随包快照本次不变。机器状态为适配新流程允许同步升级，不存第二份可编辑业务文档。
