# 元需求：Solo Delivery 模板验证与 Java DDD 示例工程

## 1. 诉求调研

### 1.1 核心诉求

当前已经具备 `solo-delivery` 技能及端到端阶段流程，但使用者尚未看到、验证和认可各阶段模板的具体内容，也无法判断模板是否符合真实研发场景。本项目需要用一次完整的“元需求”交付来暴露模板、补充约束、验证产物，并沉淀后续真实需求可复用的 Java DDD 工程框架。

### 1.2 使用者与使用场景

- 主要使用者：单人完成业务、产品、设计、开发、评审、测试和发布准备的全栈工程师。
- 当前场景：通过 `ddd` 验证 `solo-delivery` 每个阶段的模板是否完整、准确、可填写。
- 后续场景：以确认后的文档模板和 Java DDD 示例工程为基础，启动新的真实业务需求。

## 2. 背景与现状

- `solo-delivery` 已定义需求、产品、UI、技术、开发、CR、独立测试、发布和复盘阶段。
- 当前模板属于初版通用模板，尚未经过本人的真实项目校准。
- 真实交付存在必须遵守的文档格式、章节结构、Java 编码方式和 DDD 分层约束。
- DDD 代码规范文档尚未提供，不能在本阶段凭空固化具体规则。
- `ddd` 当前为空目录，没有既有代码、构建配置或项目规范。
- 用户已确认 `ddd` 同时承担模板验收和 Java DDD 参考工程两种职责，并要求通过 `AI/input` 和 `AI/output` 分离输入素材与生成文档。

## 3. 期望、预期价值与成功指标

### 3.1 期望结果

1. 清晰展示需求、产品、技术等阶段的 Markdown 模板和每个章节的填写规则。
2. 通过本次完整交付验证模板是否符合个人研发方式，并记录需要调整的地方。
3. 接收后续提供的 DDD 规范，将其转化为可执行、可校验的技术与代码约束。
4. 形成可编译、可测试、可阅读的 Java DDD 示例工程，展示典型调用和命名规范。
5. 将经确认且具有通用价值的改进反馈到 `solo-delivery` 公共模板，但不让项目自动修改公共 Skill。

### 3.2 成功指标

- 所有人类阅读的交付文档均为 Markdown，并通过模板结构校验。
- 每个阶段的必填、选填、不适用规则明确，不依赖聊天记忆才能继续。
- DDD 规范中的强制条款能够追踪到技术设计、开发任务、代码位置、CR 检查项和测试证据。
- 示例项目能够通过约定的编译、静态检查和自动化测试。
- Controller、请求/响应对象、应用服务、领域服务、仓储等典型职责和调用方向均有代码示例及反例约束。
- 至少完成一次模板评审与复盘，并区分项目特有规则和可进入公共 Skill 的规则。

## 4. 范围

### 4.1 本次范围

- 评审并逐阶段校准 `solo-delivery` 的交付文档模板。
- 定义所有文档的格式、章节、必填规则、状态和追踪要求。
- 形成需求文档、产品方案、技术方案、开发计划、开发自测、CR、测试及发布相关产物。
- 在收到 DDD 规范后，将其转化为 Java 工程的目录、分层、依赖、命名和编码约束。
- 建设 `ddd` Java DDD 示例工程，覆盖典型 Web 请求到领域及基础设施的调用链。
- 建立模板问题记录、修订依据和回归验证机制。
- 在项目根目录使用 `AI/input` 管理提供给 AI 的素材，使用 `AI/output` 管理 AI 生成的人类可读文档。

### 4.2 非目标

- 本阶段不实现具体生产业务系统。
- 在 DDD 规范文档提供并确认前，不自行发明最终 DDD 分层规则。
- 不把某个示例业务的特殊规则直接提升为所有项目的公共规范。
- 暂不建设真实 UI 页面；如果后续需要界面，再启用 UI 阶段。
- 未获得明确授权前，不部署、发布、合并代码或修改生产环境。

## 7. 业务规则与边界

| ID | 规则 |
|---|---|
| RULE-001 | 用户提供并确认的 DDD 规范优先于通用模板；与平台或仓库强制规则冲突时必须展示冲突并请求决策。 |
| RULE-002 | 文档模板定义结构和质量下限，不强迫为不适用章节编造内容。 |
| RULE-003 | 人类阅读的项目实践先记录在 `ddd/AI/output`，机器状态保留在 `.ai-delivery`；公共 `AIGenerator` 只能在用户明确要求后更新。 |
| RULE-004 | 开发自测、代码审查和独立测试必须保留不同职责与证据。 |
| RULE-005 | 示例代码必须能说明职责边界和调用方向，不能仅靠注释声称符合 DDD。 |
| RULE-006 | `SKILL.md`、`README.md`、`START.md`、`USAGE.md` 等宿主或工具约定入口保留标准名称；生成文档模板及阶段规范采用中文文件名。 |
| RULE-007 | 编号使用固定两位数字：`00` 为输入材料清单；`01`～`13` 对应交付阶段；`14`～`18` 为追踪、决策、假设、问题和交接记录。编号仅解决排序，不改变文档的业务含义。 |

## 10. 风险

- DDD 规范尚未提供，过早设计会产生返工。
- 文档模块过多可能导致小需求负担过重，需要区分必填、按需和不适用。
- 示例工程若绑定过多特定业务或基础设施，会降低复用价值。
- 单个元项目的偏好不一定适合所有项目，公共模板变更需要区分个人默认与通用规范。
- “符合 DDD”如果没有结构和自动校验，很容易退化为主观判断。
